## 2. Corrections, in this order

### 2.1 Enable path, OB1 network 8 (your question)

Today `Cmd.Enable` has two writers in OB1: network 7 (`FB_MachineReady`, output `Enable`) and network 8 (coil). Network 8 runs last, so it is the one that counts. Network 8 also writes `"DB_MOVIKIT_Robotics-5AX".enable` directly, which OB30 network 2 overwrites every cycle from `Cmd.Enable`.

Decision: network 8 is the one writer of `Cmd.Enable`. It enables the drives when the machine is on, the robot is referenced, and **somebody wants to move**. Our somebody is the Enable switch of the robot screen.

| Do | Why |
|---|---|
| Network 8: add one parallel branch `"DB_RobotMove".Man.xEnable` to the OR group with the old `x_RequestToMove` contacts | the robot screen Enable switch now enables the drives. Without it the engine sees `xSetpointActive` FALSE and gives error 5 |
| Network 8: delete the coil `"DB_MOVIKIT_Robotics-5AX".enable`, keep the coil `"DB_App".Cmd.Enable` | one writer. OB30 network 2 already passes `Cmd.Enable` to the FB |
| Network 7: disconnect the output `Enable` of `FB_MachineReady` (leave the pin empty) | second writer of `Cmd.Enable`. It loses every cycle anyway |
| Check that `#tmp_Freigabe` is assigned in a network **before** 8, every cycle | it is a temp. Read before write = random value, random enable |
| The `NOT %M3.0 AND MachineOn` branch: keep only if you know what sets `%M3.0` | if `%M3.0` is always FALSE, the drives are always enabled when the machine is on, and the Enable switch means nothing |

Later, stage 2: the AUTO switch `"DB_RobotJob".Man.xAuto` is not needed in network 8, because auto also needs the stage 1 Enable switch on (`HMI_STAGE2.md`, end of section 2).

### 2.2 OB30 network 3: `enable := TRUE`

You changed the module 2 `enable` from `TRUE` to `"DB_App".Cmd.Enable`. Put `TRUE` back. Module 2 only moves data, it has no drive power behind it. With `Cmd.Enable` FALSE the FB stops, `Srl.CommOk` falls, the status map reports comm lost, and every error on the HMI becomes error 7 instead of the real one. The robot words must flow also when the drives are off.

### 2.3 `FC_MoveSelect` is still v0.1

Network 12 shows three inputs. The queue (network 11) and the job (network 10) are already in OB1, but with v0.1 the queue head never reaches the engine: a job would build its list, push it, and wait at step 30 forever.

Regenerate `FC_MoveSelect` from `FC_MoveSelect.scl` (v0.2) and wire network 12 like `OB1_Stage2_call.scl` lines 57–65:

```
i_xHand           := "DB_RobotMove".Man.xEnable AND NOT "DB_RobotJob".Man.xAuto
i_xAuto           := "DB_RobotMove".Man.xEnable AND "DB_RobotJob".Man.xAuto
i_udtMan          := "DB_RobotMove".Man.udtReq
i_xManStart       := "DB_RobotMove".Man.xStart
i_udtQueueHead    := "DB_MoveQueue".Head
i_xQueueHeadValid := "DB_MoveQueue".xHeadValid
i_udtMoveState    := "DB_RobotMove".State
o_udtReq          => "DB_RobotMove".Req
o_xStart          => "DB_RobotMove".xReqStart
```

Hand mode behaves exactly as v0.1 while AUTO is off, so stage 1 tests are not affected. Can be done at home.

## 4. The wrong target, my best guess from the pictures

The target fields on the stage 1 screen show `0.00`. If one of them is still bound to an old tag (for example `DB_App.Path.Seg[1].X` from the old screen), `Man.udtReq.udtPose` stays at 0. Then the engine sends X 0, Y 0, Z 0, which **passes** `FC_PoseCheck` (all limits start at 0 or below), and the robot drives to the origin. That is exactly "it moves, but not to the target I wrote".

So tomorrow the six-point check of `TEST_SHEET.md` section C starts at point 2: `"DB_RobotMove".Req.udtPose` in a watch table, right after MOVE. If it shows your numbers, go on to point 3.
